# 5단계. 두 대 연동 — 10G 직결, 모델 공유, (선택) 클러스터

> 먼저 결론: **평소에는 두 대를 하나로 묶지 마세요.**
> - 묶으면: 10G 랜선을 건너는 순간 생성 속도가 40~50% 떨어지고, 버전 맞추기 등 관리가 어려워집니다.
> - 역할 분담(A=두뇌, B=보조)이 더 빠르고 안정적입니다.
> - 묶는 것이 이득인 유일한 경우: **한 대(192GB)에 안 들어가는 300GB급 모델**을 꼭 돌리고 싶을 때.
>
> 단, 10G 직결·모델 공유(5-1, 5-2)는 어떤 경우에도 유용하니 꼭 하세요.

## 5-1. 두 대를 10G 랜선으로 직접 연결

두 보드 모두 10G 랜포트가 2개씩 있습니다. 1번 포트는 공유기에, **2번 포트끼리 Cat6a 랜선 하나로 직접 연결**합니다. (스위치 필요 없음 — 요즘 랜카드는 자동 감지)

각 컴퓨터에서 인터페이스 이름 확인:

```bash
ip link   # 예: enp68s0f0(공유기용), enp68s0f1(직결용)
```

A컴퓨터 설정 (`sudo nano /etc/netplan/99-direct.yaml`):

```yaml
network:
  version: 2
  ethernets:
    enp68s0f1:            # 직결 포트 이름으로 바꾸세요
      addresses: [192.168.100.1/24]
      mtu: 9000
```

B컴퓨터는 같은 내용에 주소만 `192.168.100.2/24`.

```bash
sudo netplan apply
ping -M do -s 8972 192.168.100.2   # 점보프레임 확인 (A에서 실행)
```

속도 측정: `sudo apt install iperf3` → B에서 `iperf3 -s`, A에서 `iperf3 -c 192.168.100.2` → 9.4Gbps 근처면 정상.

## 5-2. 모델 폴더 공유 (한 번 받으면 두 대가 같이 씀)

A컴퓨터를 모델 창고로:

```bash
# A컴퓨터 (내보내기)
sudo apt install -y nfs-kernel-server
echo '/models 192.168.100.0/24(ro,async,no_subtree_check)' | sudo tee -a /etc/exports
sudo exportfs -ra
```

```bash
# B컴퓨터 (가져오기)
sudo apt install -y nfs-common
sudo mkdir -p /models-a
sudo mount -t nfs -o ro,nconnect=8,rsize=1048576 192.168.100.1:/models /models-a
# 부팅 시 자동: /etc/fstab에 추가
echo '192.168.100.1:/models /models-a nfs ro,nconnect=8,rsize=1048576 0 0' | sudo tee -a /etc/fstab
```

주의: 자주 재시작하는 서비스는 NFS 로딩(10G에서 70GB ≈ 1~2분)이 느리니, 상시 쓰는 모델은 각자 SSD에 복사해 두는 게 좋습니다.

## 5-3. (선택) 정말 거대한 모델을 두 대에 걸치기

### 쉬운 방법: llama.cpp RPC

```bash
# 빌드 시 RPC 켜기 (양쪽 다)
cmake -B build -DGGML_CUDA=ON -DGGML_RPC=ON && cmake --build build -j

# B컴퓨터 (일꾼): 절대 외부망에 노출 금지 — 직결 주소에만 바인딩
build/bin/ggml-rpc-server -H 192.168.100.2 -p 50052 -c

# A컴퓨터 (대장):
build/bin/llama-server -m /models/거대모델.gguf -ngl 999 \
  --rpc 192.168.100.2:50052 -c 16384 --host 0.0.0.0 --port 8080
```

- 예상 성능: 같은 GPU를 한 몸에 넣었을 때의 **약 절반**. 실측: 72B에서 11.1 → 5.9 토큰/초.
- 그래도 CPU 오프로딩보다는 훨씬 빠름 (실측 17 → 53 토큰/초). "안 들어가는 모델을 들어가게" 하는 용도.

### 본격 방법: vLLM + Ray (동시 요청 많을 때)

- 원칙: **텐서 병렬은 컴퓨터 안에서만, 컴퓨터 사이는 파이프라인 병렬.** 10G로 노드 간 TP는 불가능한 수준입니다.
- 두 대의 GPU 수를 맞춰야 합니다 (예: 양쪽 다 3090을 7장씩 → `-tp 7`은 불가하니 실제로는 8장씩 맞추는 게 이상적, 아니면 4장씩 → `-tp 4 -pp 2`).
- 도커로 양쪽 환경을 똑같이 맞추는 게 공식 권장:

```bash
# A(대장): vLLM 저장소의 examples/ray_serving/run_cluster.sh 사용
bash run_cluster.sh vllm/vllm-openai 192.168.100.1 --head /models \
  -e VLLM_HOST_IP=192.168.100.1 -e NCCL_SOCKET_IFNAME=enp68s0f1 \
  -e GLOO_SOCKET_IFNAME=enp68s0f1 -e NCCL_IB_DISABLE=1
# B(일꾼): 같은 명령에서 --worker, VLLM_HOST_IP=192.168.100.2
# A 컨테이너 안에서:
vllm serve <모델> --tensor-parallel-size 8 --pipeline-parallel-size 2 \
  --distributed-executor-backend ray
```

- 파이프라인 병렬은 대역폭을 거의 안 먹어서 10G로 충분하지만, **단일 대화 속도는 느려집니다** (동시 요청 처리량용).

### 관리를 편하게: GPUStack (추천 오케스트레이터)

여러 대·여러 엔진·섞인 GPU를 웹 화면 하나로 관리하고 싶으면 GPUStack(v2.2+)을 쓰세요.
GGUF는 llama.cpp 계열로, safetensors는 vLLM으로 자동 배치하고, 이기종 GPU(2080Ti 포함)도 지원합니다.

```bash
# A컴퓨터 (서버): 도커로 설치 (공식 권장)
docker run -d --name gpustack --restart always --gpus all \
  -p 80:80 -v gpustack-data:/var/lib/gpustack gpustack/gpustack
# B컴퓨터 (일꾼): 웹 화면에서 발급받은 토큰으로
docker run -d --name gpustack-worker --restart always --gpus all \
  gpustack/gpustack --server-url http://192.168.100.1 --token <토큰>
```

## 5-4. 참고: exo는 이제 답이 아님

한때 유행했던 exo(여러 기기를 묶는 도구)는 애플 실리콘 전용으로 방향을 틀었고, 리눅스는 CPU만 지원합니다. 엔비디아 2대 구성에는 쓸 수 없습니다.
