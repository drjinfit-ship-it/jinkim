# 상시 녹음 → 해석 → 선제 실행 → 보고 파이프라인

목표: **"오늘 녹음된 모든 것을 빠르게 해석해 의견을 주고, 나올 일의 절반을 이미 해놓고 보고한다."**

## 0. 결론

**가능합니다. 그리고 하드웨어는 이미 필요 이상입니다.**

어려운 부분은 GPU가 아니라 다른 세 곳에 있습니다.

| 실제 난이도 | 왜 |
|---|---|
| 🔴 **STT 품질** | 여기서 틀리면 하위 전 과정이 쓰레기가 됩니다. 한국어 + 전문용어 + 다화자 + 잡음 |
| 🔴 **"절반 먼저"의 신뢰 구축** | 기술이 아니라 운영 문제. 한 번 잘못 보낸 메일이 시스템 전체 신뢰를 무너뜨립니다 |
| 🟡 **액션아이템 추출 정밀도** | 과다 추출 = 노이즈, 과소 = 놓침. 사람 피드백으로 수 주간 튜닝 필요 |
| 🟢 연산 능력 | 이미 과잉. Mac Studio만으로 8시간 녹음을 9~22분에 전사 |

## 1. 전체 파이프라인

```
[1 캡처]  아이폰 / 워치 / 펜던트 / 맥 마이크
             ↓ 폴더 감시 (launchd WatchPaths)
[2 전사]  Mac Studio — whisperx-mlx 또는 Core ML/ANE + pyannote
             ↓ 세그먼트 JSONL (타임스탬프 + 화자)   ★ 상시 저전력, GPU 비경합
[3 추출]  Station A — 27B ×8 replica, 세그먼트 병렬
             ↓ 구조화 JSON: 결정/액션/약속/질문/리스크/톤
[4 종합]  Mac Studio — 27B 262K 컨텍스트 (하이브리드 선형 어텐션)
             ↓ 하루의 서사, 모순, 놓친 것, 의견
[5 실행]  ★ "절반 먼저" — 가역성 게이트로 분류 후 자동 수행
             ↓
[6 보고]  "12개 액션. 8개는 초안까지 완료. 4개는 판단 필요."
```

각 단계가 어느 계층에서 도는지는 `FLEET.md` 라우팅 정책 그대로입니다.
**녹음 데이터는 전 과정에서 외부로 나가지 않습니다** — 이게 로컬 인프라의 존재 이유입니다.

## 2. 단계별 설계

### 2-1. 캡처

| 방식 | 장점 | 단점 |
|---|---|---|
| 아이폰 음성메모 + iCloud | 추가 장비 없음 | 수동 시작, 배터리 |
| 전용 펜던트/레코더 | 상시성 최고 | 별도 장비, 동기화 |
| 맥 마이크 (사무실 상주) | 자동, 무제한 | 자리 밖은 못 잡음 |

**권장**: 사무실은 Mac Studio 상시 캡처, 이동 중은 아이폰. 둘 다 같은 감시 폴더로 떨굽니다.

```
$MAI_HOME/inbox/audio/     ← 여기에 파일이 떨어지면 파이프라인 자동 기동
```

**용량**: Opus 24kbps로 인코딩하면 8시간/일 ≈ **86MB/일 ≈ 31GB/년**.
무손실(16bit/16kHz mono)로 보관해도 연 168GB입니다.
**총 3TB(내장 1TB + 외장 2TB)에서 오디오는 전혀 문제가 아닙니다** —
진짜 용량을 먹는 건 모델입니다(27B 15GB, Flash-Next REAP-288 68GB).

⚠️ **녹음 고지**: 본인이 참여한 대화 녹음은 합법이지만, 상대가 있는 자리라면
고지하는 편이 안전합니다. 업무 성격상 민감정보(의료·개인정보)가 섞인다면
보관 기간과 접근 통제를 먼저 정하고 시작하세요. 이건 기술이 아니라 정책 문제입니다.

### 2-2. 전사 (STT) — Mac Studio에서 상시 저전력으로

> **2026-08-30 정정**: 초판은 전사를 Station B에 배치했으나 **이는 설계 모순이었습니다.**
> `GPU-STATIONS.md`에서 Station B를 "자유롭게 재부팅하는 실험 머신"으로 못박아 놓고
> 그 위에 상시 지연민감 서비스를 올린 셈입니다. **Mac Studio가 맞습니다.**

#### 왜 Mac Studio인가

| 근거 | 내용 |
|---|---|
| **전력** | Station B 가동 ~3.5kW vs Mac Studio 부하 시 **60~120W**. 전사하겠다고 3.5kW를 켜는 건 30배 낭비 |
| **아키텍처 일관성** | Station B는 재부팅 자유 머신. 상시 서비스를 얹으면 안 됨 |
| **데이터 지역성** | 오디오가 맥에 떨어짐. GB 단위 파일을 네트워크로 옮길 이유가 없음 |
| **화자분리 가능** | pyannote 3.1이 onnxruntime을 제거해 순수 PyTorch — MPS 정상 동작 |
| **단순성** | 한 대, launchd 하나. 기기 간 의존성이 사라짐 |

#### ⚠️ 구현 선택이 하드웨어보다 중요합니다

**같은 M3 Ultra에서 구현에 따라 20배 이상 차이 납니다.**

| 구현 | 실시간 배수 | 8시간 녹음 처리 |
|---|---|---|
| `mlx-whisper` large-v3 (기본) | 2~3× | **3시간+** ❌ 상시 운영 불가 |
| large-v3-turbo MLX | 9.1× | 53분 |
| **Core ML / ANE dispatch** | 22× | 22분 |
| **`whisperx-mlx`** | 최대 52× | **9분** ✅ |

기본 `mlx-whisper`를 쓰면 8시간 녹음에 3시간이 걸립니다. 이건 "상시 저전력"이 아닙니다.
**`whisperx-mlx` 또는 Core ML 경로를 쓰세요.**

#### ★ Neural Engine을 쓰면 LLM과 경합하지 않습니다

Mac Studio의 GPU는 [마이] 27B 인스턴스들이 점유합니다(`QWEN38-NEXT.md` 6-6절).
STT까지 GPU를 쓰면 전사 중에 [마이] 응답이 느려집니다.

**Core ML로 Neural Engine(ANE)에 dispatch하면 GPU를 건드리지 않습니다.**
그리고 ANE는 GPU보다 훨씬 저전력입니다. 이게 "상시 저전력"의 진짜 답입니다.

```
GPU  →  Qwen3.8-27B ×2~3 (LLM 추론)      ← 경합 없음
ANE  →  Whisper 전사                      ↙
CPU  →  pyannote 화자분리 (또는 MPS)
```

#### 메모리 예산 (96GB)

```
27B ×2 인스턴스       30 GB     (병렬 추출용)
임베딩 + 리랭커         3 GB
Whisper large-v3        3 GB
pyannote                1 GB
─────────────────────────────
합계                  ~37 GB / 96 GB   → 여유 59GB
                                        (Flash-Next 39GB를 얹어도 76GB)
```

#### 화자분리

pyannote 3.1은 MPS를 지원합니다 — 실측 기준 **CPU 3분 vs MPS 20초**(동일 파일).
M3 Ultra는 CPU 28코어도 강력하므로 GPU 경합이 걱정되면 CPU로 돌려도 됩니다.

```python
pipeline.to(torch.device("mps"))   # 또는 "cpu"
```

#### 도메인 어휘 사전이 품질의 절반입니다

업무 전문용어, 사람 이름, 제품명, 약어를 `config/vocab.txt`에 모아
`initial_prompt`로 주입하거나 후처리 교정합니다.
이걸 안 하면 전문용어가 전부 엉뚱하게 전사되어 하위 단계가 무의미해집니다.

**화자 등록**: 본인 목소리를 등록해 두면 "내가 한 말 vs 상대가 한 말"을 구분할 수 있고,
이게 액션아이템 귀속(누가 하기로 했나)에 결정적입니다.

#### 스테이션에 남겨둘 것 — 대량 백필

**일상 전사는 맥, 대량 재처리는 스테이션**입니다.
나중에 모델을 바꾸거나 어휘 사전을 크게 개선해 **수개월치 아카이브를 재처리**할 때,
맥으로는 며칠이 걸리는 작업을 Station B가 몇 시간에 끝냅니다.
그때만 켜면 됩니다 — 그게 3.5kW를 쓸 만한 유일한 경우입니다.

### 2-3. 1차 추출 — 저비용 대량

**Station A, 27B ×8 replica.** 5~10분 세그먼트 단위로 병렬 처리.
`FLEET.md` 라우팅 규칙의 "쉽지만 만 번"이 정확히 여기입니다.

세그먼트당 구조화 JSON을 뽑습니다:

```json
{
  "segment_id": "2026-08-30T14:05",
  "topic": "3분기 예산 검토",
  "decisions": [{"what": "...", "who": "...", "confidence": 0.8}],
  "action_items": [
    {"task": "...", "owner": "나", "due": "2026-09-05",
     "type": "code|doc|research|contact|schedule", "reversible": true}
  ],
  "commitments": [], "open_questions": [], "risks": [],
  "tone": "긴장|평온|갈등", "unresolved": []
}
```

`type`과 `reversible`이 5단계 실행 계층의 입력이 됩니다.

### 2-4. 2차 종합 — 하루치를 한 컨텍스트에

하루 8시간 녹음 ≈ **8만~12만 토큰**. **27B의 262K 컨텍스트에 하루치가 통째로 들어갑니다.**
27B도 64층 중 48층이 Gated DeltaNet(선형 어텐션)이라 KV가 상수 상태로 압축됩니다 —
롱컨텍스트를 위해 Flash-Next가 필요하지 않습니다 (`QWEN38-NEXT.md` 6-4절).

세그먼트별 요약만 봐서는 알 수 없는 것들을 여기서 잡습니다:
- **모순**: 오전에 A라고 했는데 오후에 B라고 함
- **미해결**: 제기됐지만 아무도 답하지 않고 넘어간 질문
- **패턴**: 이번 주에 세 번째 나온 같은 불만
- **의견**: "이 결정은 지난주 결정과 충돌합니다"

⚠️ **성능 주의**: 10만 토큰 prefill은 Mac Studio에서 **수 분** 걸립니다.
실시간이 아니라 **하루 마감 배치**로 돌리세요. 즉시 피드백은 3단계(세그먼트 단위)가 담당합니다.

**계층적 요약**을 쓰면 더 안정적입니다: 세그먼트 → 시간별 → 하루.

### 2-5. ★ 실행 계층 — "절반 먼저"의 정의

여기가 이 시스템의 핵심이자 가장 위험한 부분입니다.

#### 가역성 게이트 (Reversibility Gate)

**"절반"의 정의는 애매한 비율이 아니라 명확한 경계입니다:
되돌릴 수 있는 것은 전부 하고, 되돌릴 수 없는 것 앞에서 멈춘다.**

| 자동 실행 ✅ (가역) | 사람 승인 필요 ⛔ (비가역) |
|---|---|
| 파일·문서 초안 생성 | **이메일·메시지 발송** |
| 브랜치 생성, 커밋 (푸시 X) | main 브랜치 푸시, 머지 |
| 조사·자료 수집·요약 | **결제, 계약, 주문** |
| 일정 후보 계산 | 일정 확정·초대 발송 |
| 테스트 작성·실행 | 프로덕션 배포 |
| 데이터 분석·리포트 | **외부 API 쓰기** |
| 체크리스트·계획 수립 | 파일·레코드 삭제 |

이 경계를 코드로 강제하세요. LLM의 판단에 맡기지 마세요.
실행기는 `reversible: false`인 액션을 **아예 실행할 수 없는 구조**여야 합니다.

#### 타입별 실행 경로

| type | 실행 주체 | 산출물 |
|---|---|---|
| `code` | **Claude Code** (worktree 격리) | 브랜치 + 커밋 + 테스트 통과 상태 |
| `doc` | 로컬 27B | 초안 마크다운 |
| `research` | 로컬 + 웹 검색 | 조사 노트 + 출처 |
| `contact` | 로컬 27B | **초안만.** 발송 절대 금지 |
| `schedule` | 캘린더 읽기 | 가능 시간 후보 목록 |

#### 신뢰 구축은 단계적으로

**처음부터 자동 실행 범위를 넓히지 마세요.** 권장 순서:

```
1주차  전부 초안만. 사람이 채택률을 본다
2~4주  채택률 80% 넘는 타입만 자동 실행 승격
2개월~ 코드 작업까지 자동 (단 푸시는 여전히 수동)
```

채택률을 기록하지 않으면 언제 범위를 넓혀도 되는지 알 수 없습니다.
`memory/metrics/adoption.jsonl`에 매일 남기세요.

   · "리소스 부족"이 이번 주 세 번째입니다. 구조적 문제일 수 있습니다.

## 3. 어디서 실패하는가 — 미리 알아야 할 것

| 실패 모드 | 대응 |
|---|---|
| **전사 오류가 전 과정을 오염** | 도메인 어휘 사전 + 신뢰도 낮은 구간 표시. 원문 타임스탬프를 항상 보존해 사람이 되짚을 수 있게 |
| **액션 과다 추출로 노이즈** | 초기엔 재현율보다 정밀도. "확실한 것만" 프롬프트 |
| **자동 실행이 틀린 일을 함** | 가역성 게이트. 그리고 **모든 자동 실행은 되돌리는 방법을 함께 기록** |
| **하루 종일 녹음의 피로** | 전부 처리하려 하지 말 것. 회의·통화만 잡고 잡담은 버리는 필터 |
| **시스템을 안 믿게 됨** | 채택률 측정. 낮으면 범위를 **줄이세요**. 늘리지 말고 |

## 4. 구축 순서 — 4단계, 각 1~2주

```
Phase 1  캡처 + 전사만                  ← 여기서 STT 품질을 잡는다
         inbox 감시 → 전사 → 텍스트 저장. 그게 전부.
         2주간 전사문만 읽어보며 어휘 사전을 채운다.

Phase 2  추출 + 하루 브리프
         액션아이템 추출 → 마감 브리프 생성. 실행은 없음.
         채택률 측정 시작.

Phase 3  실행 계층 (초안만)
         doc/research 타입만 초안 생성. 가역성 게이트 구현.

Phase 4  코드 자동화 + 범위 확대
         Claude Code 연동. 채택률 80% 넘은 타입만 승격.
```

**Phase 1을 건너뛰지 마세요.** STT 품질이 안 나오는 상태에서 상위 단계를 만들면
전부 다시 만들게 됩니다.

## 5. 실행 골격

`mai/pipeline/` 에 각 단계의 실행 가능한 골격이 있습니다.

| 파일 | 역할 |
|---|---|
| `watch.sh` | `inbox/audio/` 감시 → 파이프라인 기동 (launchd) |
| `transcribe.py` | Mac Studio 전사 + 화자분리 (STT 백엔드 교체 가능) |
| `extract.py` | Station A 병렬 구조화 추출 |
| `synthesize.py` | Mac Studio Flash-Next 하루 종합 |
| `gate.py` | **가역성 게이트** — 비가역 액션 실행 차단 |
| `report.py` | 마감 브리프 생성 |

모델이 바뀌어도 파이프라인 코드는 그대로입니다.
